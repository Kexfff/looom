# Установка начальной системы

Историческая установка первой VM 2026-10-04. Для текущего Rust-менеджера
и будущего реального компьютера использовать [руководство пилота](physical-pilot.md).

Этот этап устанавливает обычный writable Arch в `@bootstrap` для дальнейшей
разработки read-only релизов. Механизм атомарных релизов и KDE пока относятся
к следующим этапам [плана](mvp-plan.md).

## Что фиксируется

- Официальные репозитории Arch `core` и `extra` из архива `2026/10/03`.
- Запрошенные пакеты: [packages.txt](../configs/bootstrap/packages.txt).
- Параметры диска, пользователя, сети и подтомов: [install.env](../configs/bootstrap/install.env).
- Полный состав установленных пакетов, SHA-256 скачанных архивов и баз репозиториев.
- Нормализованный [bootstrap lock](../manifests/bootstrap/lock.json): все 210 пакетов,
  версии с epoch, имена архивов, SHA-256 архивов и detached signatures.
- Фактические fstab, kernel cmdline, настройки pacman, mkinitcpio и GRUB.
- XML VM до и после настройки UEFI, контрольные суммы прошивки и журнал выполнения.

Процесс воспроизводит пакетный состав и настройки. UUID файловых систем,
machine-id, host keys и password hashes являются индивидуальным состоянием VM.
Доступность зафиксированных файлов архива необходима для повторной установки;
их копии также остаются в `/var/cache/pacman/pkg` установленной VM.

Lock можно повторно сформировать из сохранённого evidence:

```bash
python3 scripts/capture-bootstrap-lock.py \
  docs/runs/2026-10-04-bootstrap/evidence manifests/bootstrap/lock.json \
  --archive-date 2026/10/03
```

Перед признанием повторной установки эквивалентной сравнить полный пакетный lock
с эталонным. Контрольная сумма UKI конкретного запуска хранится отдельно: образ
включает индивидуальный UUID корня, поэтому не должен совпадать у разных VM.

## Параметры текущей VM

- libvirt: `qemu:///system`, домен `Cachyos` (сохранено исходное имя VM).
- MAC: `52:54:00:7b:23:63`; исходный адрес SSH: `192.168.122.91`.
- 6 vCPU, RAM 8 GiB, виртуальный VirtIO-диск 60 GiB, платформа Q35.
- UEFI: OVMF 4 MiB без Secure Boot, отдельная сохраняемая NVRAM.
- Приоритет загрузки после установки: диск, затем Arch ISO для восстановления.
- GPT: `/dev/vda1` ESP 2 GiB FAT32; `/dev/vda2` Btrfs на оставшемся месте.
- Подтомы: `@bootstrap`, `@home`, `@var`, `@state`.
- Монтирования: `/`, `/home`, `/var`, `/var/lib/looom`; ESP — `/efi`.
- Пользователь `codex`, UID/GID 1000, группа `wheel`; hostname `looom-vm`.
- Часовой пояс Europe/Moscow, локаль en_US.UTF-8, также сгенерирована ru_RU.UTF-8.

## Учётные данные и доступ

Выделенный ключ управления хранится на хосте в `.local/vm-access/id_ed25519`;
весь `.local/` исключён из Git. В VM передаётся только публичный ключ.
SSH принимает ключ для `root` и `codex`; вход по SSH с паролем выключен.

Первоначальный пароль для локального входа `root` и `codex` инициализируется
из предоставленного пользователем пароля root в live-среде. Сценарий переносит
hash через stdin, не печатает и не сохраняет его в журнал, конфигурацию или lock.
Сами учётные записи bootstrap используют обычный защищённый `/etc/shadow`.
Отдельное постоянное предоставление пароля для read-only релизов будет реализовано
на следующем этапе; текущий bootstrap не является публикуемым базовым релизом.

У `codex` настроен sudo без пароля для управления этой тестовой VM.
Это явная настройка лабораторного профиля, а не требование для будущей системы.

Приватные host keys остаются только внутри VM. До первого запуска с диска
их публичные fingerprints получают через аутентифицированное SSH-соединение
с live-средой и добавляют в локальный known_hosts, чтобы проверить новую систему.

## Повторная установка

1. Подготовить disposable VM с параметрами выше и загрузить Arch ISO.
2. Настроить SSH-доступ к live-среде и подготовить публичный management key.
3. При другой VM изменить `install.env`: имя интерфейса, MAC и размер диска.
   Сценарий требует QEMU/KVM, диск `/dev/vda` указанного размера, ожидаемый MAC,
   root в live-среде и отсутствие смонтированных разделов целевого диска.
4. Скопировать каталоги `scripts/` и `configs/` в `/run/looom-bootstrap` внутри VM,
   публичный ключ — в `/run/looom-management.pub`.
5. В VM выполнить:

   ```bash
   bash /run/looom-bootstrap/scripts/install-bootstrap.sh --erase-disk=/dev/vda
   ```

   Операция полностью уничтожает содержимое указанного виртуального диска.
   Проверки целевого устройства выполняются до форматирования. Сценарий
   не предназначен для повторного применения к уже установленной системе.

6. Сохранить каталог `/run/looom-bootstrap/evidence` и полный вывод установки
   до выключения live-среды. Копия evidence и несекретные исходники установки
   также находятся в `@state`, в `/var/lib/looom/bootstrap-evidence` и `bootstrap-source`.
7. Подготовить XML UEFI на хосте:

   ```bash
   virsh -c qemu:///system dumpxml --inactive Cachyos > before.xml
   python3 scripts/prepare-vm-uefi.py before.xml uefi.xml --mac 52:54:00:7b:23:63
   virsh -c qemu:///system define --validate uefi.xml
   ```

   Это меняет persistent-конфигурацию. Прошивка вступает в силу после полного
   выключения и запуска VM. Пути OVMF задаются опциями `--code` и `--vars`;
   при повторной установке той же VM нужно отдельно учесть старое содержимое NVRAM.

8. Выключить VM и запустить её с диска. GRUB установлен и в именованном каталоге
   `EFI/looom`, и по fallback-пути `EFI/BOOT/BOOTX64.EFI`.
9. Проверить адрес через DHCP leases libvirt, подключиться ключом и выполнить
   `scripts/verify-bootstrap.sh` внутри VM под root.

Пример подключения из корня проекта:

```bash
ssh -i .local/vm-access/id_ed25519 \
  -o UserKnownHostsFile=.local/vm-access/known_hosts \
  -o StrictHostKeyChecking=yes codex@192.168.122.91
```

## Особенности установки

- pacstrap сначала устанавливает систему с собственной `/var`.
- База pacman переносится в `/usr/lib/looom/pacman`, в `pacman.conf` задаётся `DBPath`.
- `/var/lib/pacman` становится compatibility symlink в базу активного корня.
- Затем данные `/var` переносятся в `@var` и подключаются постоянные подтомы.
- В UKI явно указан `root=UUID=... rootflags=subvol=@bootstrap rw`.
- GRUB и `grubenv` находятся на общей ESP, в `/efi/looom/grub`.
- Меню генерируется сценарием по известным артефактам, не через обнаружение
  других систем `grub-mkconfig`.
- Присутствует обработка `saved_entry` и `next_entry`; надёжность однократной
  загрузки проверяется отдельным опытом после базовой установки.
- NetworkManager использует DHCP и MAC client-id; SSH, timesyncd, guest agent
  и serial getty включены. Ядро выводит сообщения на экран и ttyS0.

## Проверки

Перед выключением live-среды: синтаксис sudoers, SSH и GRUB, генерация UKI,
полный пакетный inventory и контрольные суммы артефактов.
После загрузки с диска: UEFI, правильные подтомы и файловые системы,
согласованная база pacman, активные сервисы, SSH для пользователя и root,
sudo, отсутствие failed units, валидный fstab и наличие UKI.
