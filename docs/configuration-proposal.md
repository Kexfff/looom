# Предложение схемы конфигурации v1

Дата: 2026-10-06. Документ содержит первоначальное предложение и будущие ресурсы.
Его базовое подмножество реализовано строгим YAML-парсером и нативным Rust CLI.
Не все поля полного примера ниже поддерживаются: актуальные границы и рабочие
примеры приведены в [контракте looom 0.2](native-rust.md).

Согласовано 2026-10-06: для MVP оставляем предложенные базовые функции,
типовые модули и правила владения, включая управление критическими конфигами
через менеджер. Конкретные имена полей остаются проектом API.
Позже для таких конфигов, как `fstab`, рассмотрим отдельные обработчики:
они должны согласовывать пользовательские настройки с контрактом загрузки,
а не просто заменять сгенерированный файл произвольным текстом.

Документ развивает [архитектурный контракт](architecture.md).
Принятые требования к read-only релизам, локальным исключениям и паролям
сохраняются. Rust, названия полей и ограничения MVP здесь предлагаются.

## Назначение и границы

looom управляет декларацией базовой системы, сборкой, проверкой, публикацией,
выбором загрузки и откатом. pacman остаётся пакетным backend.
Первый backend — официальный Arch; CachyOS добавляется отдельным профилем.

Декларация описывает целевой состав, а не последовательность изменений.
Каждый корень MVP собирается заново. Предыдущий релиз используется для сравнения,
но не как источник неописанных файлов или настроек.

Домашние каталоги, данные служб, локальные исключения и секреты сохраняются
отдельно. Их удаление или миграция не являются побочным эффектом сборки и отката.
Откат базы не гарантирует откат форматов данных служб.

## Документы и состояние

| Объект | Назначение |
| --- | --- |
| `base.yaml` | Редактируемое описание базовой системы |
| `files/` | Дополнительные файлы, включаемые в релиз |
| `base.lock` | JSON с точным пакетным составом и идентификацией рецептов |
| Снимок входных данных релиза | Проверенная декларация, байты файлов, lock и их контрольные суммы |
| Состояние машины | UUID разделов, пути монтирования, machine-id, назначения UID/GID, локальные данные, секреты |
| Журнал операций | Сборки, публикации, выбор загрузки, подтверждения и восстановление |

UUID разделов и фактический ID корня не задаются в переносимой декларации.
Они подставляются при формировании загрузочного образа для конкретной машины
и фиксируются в метаданных релиза. Выбор GRUB и раскладка диска относятся
к установке и состоянию машины; откат базы не откатывает эту инфраструктуру.

`apps.yaml` и управление пользовательскими приложениями — следующий этап.

## Пример полной декларации

Это пример предлагаемого API для нашей VM, не конфигурация, применённая к ней.
Имена secret — ссылки на отдельно подготовленные учётные данные.
Файл из `files/` в примере также должен существовать в исходном комплекте.

```yaml
schema: 1

source:
  profile: arch
  snapshot: "2026-10-03"

system:
  hostname: looom-vm
  timezone: Europe/Moscow
  locale: en_US.UTF-8
  console_keymap: us

kernel:
  package: linux
  extra_command_line: []

desktop:
  environment: plasma

packages:
  - openssh
  - htop

accounts:
  user:
    name: codex
    uid: 1000
    gid: 1000
    groups: [wheel]
    shell: /bin/bash
    password_secret: login-codex
  root:
    password_secret: login-root

units:
  sshd.service: enabled
  bluetooth.service: masked

files:
  /etc/ssh/sshd_config.d/20-looom.conf:
    content: |
      PasswordAuthentication no
      KbdInteractiveAuthentication no
    mode: "0644"
  /etc/sysctl.d/90-looom.conf:
    source: files/90-looom.conf
    mode: "0644"

persistent:
  directories:
    /etc/NetworkManager/system-connections:
      id: network-connections
      owner: root
      group: root
      mode: "0700"
    /etc/looom-local:
      id: local-settings
      owner: root
      group: root
      mode: "0755"

health:
  required_units:
    - sshd.service
```

## Значение разделов

### Источники и пакеты

- `source.profile` выбирает встроенный версионированный рецепт. В MVP разрешён
  только `arch`, с фиксированными правилами репозиториев и доверия.
- `source.snapshot` задаёт согласованную дату источников для разрешения lock.
  Дата сама по себе не заменяет версии, архивы и подписи в lock.
- `packages` — дополнительные явно запрошенные пакеты. Пакеты системного профиля,
  ядра, рабочего стола и их зависимости добавляются автоматически, но полностью
  видны в плане и lock с указанием причин включения.
- Списка исключений в MVP нет: нельзя без объяснения удалить обязательный пакет
  профиля или зависимость. Для исключения необязательной программы меняется запрос
  пакетов либо выбранный модуль, а не итоговый список зависимостей.
- Удаление пакета из `packages` снимает явный запрос. Пакет останется, если нужен
  другой части декларации; план должен показать эту причину.
- Имена пакетов перечисляются явно. Группы, AUR, URL произвольных архивов
  и неявный выбор между поставщиками зависимостей откладываются.
  Неоднозначность поставщика при создании lock требует явного выбора.

### Системные модули

- `system` генерирует hostname, timezone, locale и раскладку консоли.
  В MVP одна системная locale; дополнительные locale можно добавить расширением схемы.
- `kernel.package` в MVP — `linux` либо `linux-lts`, одно ядро на релиз.
- `kernel.extra_command_line` — дополнительные аргументы. `root`, `rootflags`,
  выбор read-only корня и прочие параметры загрузочного контракта зарезервированы
  менеджером; аргументы, противоречащие им, отклоняются.
- `desktop.environment` — `none`, `plasma` либо `niri`. `desktop.sessions: [niri]`
  добавляет Niri/Quickshell рядом с Plasma. Графические модули выбирают SDDM,
  системные компоненты звука и обязательные интеграции. Точный состав модуля
  версионируется и раскрывается в плане, а не зависит от скрытых настроек хоста.
- `packages_from` подключает ограниченные относительные package sets; freeze
  сохраняет их раскрытые имена. [Импорт зависимостей контейнерных установщиков](apps.md#системные-зависимости-без-ручного-переноса-каждого-пакета).
- Модуль возвращает запросы пакетов, файлы, состояния units, требования к локальному
  состоянию и проверки. Модули MVP встроены в менеджер; загрузки исполняемых
  пользовательских плагинов нет.

### Учётные записи

Оценка текущей реализации и требования перед MVP:
[безопасность password credentials](credentials-security.md).

- `accounts.user` описывает одного личного пользователя. UID/GID обязательны.
  Группы и shell должны существовать в собранной системе.
- `accounts.root` описывает только ссылку на пароль root. Имя, UID/GID root фиксированы.
  Отсутствие ссылки означает заблокированный пароль, а не пустой пароль.
- Ссылка указывает на password hash в защищённом постоянном хранилище. Сам hash
  не включается в YAML, lock, снимок входных файлов и read-only корень.
- Ссылки проверяются перед пробной загрузкой; объявленная, но отсутствующая
  credential блокирует её. Обновление значения credential не требует нового релиза.
- Предлагается сохранить проверенную модель: `passwd`/`group` в корне,
  `shadow`/`gshadow` в `/run`, сформированные из отдельных credentials.
- На установленной машине изменение имени личного пользователя, UID/GID либо
  идентификатора его password secret в MVP блокируется с объяснением необходимости
  миграции. Создание декларации для новой машины этим не ограничивается.
- Системные UID/GID резервируются в отдельном регистре и не переиспользуются.
  В корень включаются нужные аккаунты; сохранение назначения в регистре не означает
  необходимость включать все исторические аккаунты в каждый новый релиз.

### Units и проверки

`units` задаёт состояния системных unit-файлов точными именами, включая `.service`,
`.socket` и `.timer`; шаблоны имён и shell-команды не принимаются.

| Значение | Смысл |
| --- | --- |
| `enabled` | Настроить предусмотренное unit-файлом включение при загрузке |
| `disabled` | Убрать включение при загрузке; зависимости или активация всё ещё могут запустить unit |
| `masked` | Запретить запуск unit |

`enabled`/`disabled` требуют наличия unit и поддержки применяемого способа включения;
static unit проверяется как зависимость и не включается искусственно.
Для `masked` допускается отсутствующий unit: это явный запрет на будущую активацию.

Эффективный набор строится из профиля, модулей и декларации. Необязательное правило
модуля можно заменить явно; обязательные units защищены от отключения или маскирования.
Неописанные vendor presets не должны становиться скрытым источником включённых служб.
План перечисляет весь эффективный набор, обязательность и происхождение правил.

`health.required_units` добавляет проверки к обязательным проверкам менеджера
и модулей. Обязательные проверки корня, загрузочного образа, аккаунтов и монтирований
нельзя отключить. Статус SDDM не доказывает работоспособность Wayland-сессии:
в MVP окончательное подтверждение рабочего стола остаётся ручным.

## Владение путями

Есть четыре источника содержимого: пакет, системный модуль, пользовательская
декларация и постоянное локальное состояние. У конечного пути один эффективный
владелец; допустимые замены фиксируются в манифесте.

1. **Обычные пакетные файлы** остаются как установлены из lock.
2. **Модуль** может заменить заранее описанные конфигурационные файлы пакета.
   Два модуля не могут независимо генерировать один конечный файл.
3. **Пользовательский файл** может создать новый конфиг в `/etc`.
   Замена уже существующего пакетного файла требует `replace_package_file: true`.
   Замена файла системного модуля этим флагом не разрешается.
4. **Локальный каталог** целиком предоставляется из постоянного состояния.
   Внутри него нельзя одновременно объявлять файлы или генерировать настройки модулем.
5. Пакетный родительский каталог сам по себе не запрещает добавление дочернего файла.
   Проверка вложенных конфликтов касается ресурсов, владеющих всем поддеревом,
   прежде всего постоянных монтирований.

Зарезервированы файлы аккаунтов, `fstab`, `machine-id`, `resolv.conf`, настройки
пакетного backend и файлы идентификации релиза; также служебные каталоги `.wants`
и `.requires`, ссылки включения и маски units. Весь `/etc/systemd/system` целиком
не резервируется. Полный список входит в версионированный системный рецепт и виден
в плане. Пользовательские unit-файлы и drop-in файлы необязательных units допустимы
вне конфликтующих путей. Изменение определения обязательного unit в MVP выполняется
только через поддерживаемые настройки его модуля.

Для изменения конфигурации, принадлежащей модулю, используем параметр модуля,
поддерживаемый конфигурационный фрагмент либо отключение необязательного модуля
и явное управление его файлами. Если необходимого параметра нет у обязательного
модуля, требуется расширить модуль; универсального обхода его правил в MVP нет.

`files` в MVP создаёт только обычные файлы внутри `/etc`. Для каждого файла нужно
ровно одно из `source` и `content`; `owner`/`group` по умолчанию `root`, `mode` —
`"0644"`. Режим записывается строкой из четырёх восьмеричных цифр; специальные
setuid/setgid/sticky биты в этом ресурсе MVP не поддерживаются.

Пути назначения абсолютны. Источники относительны каталогу декларации и не могут
выйти за исходный комплект. Родительские переходы и обход через симлинки отклоняются.
Все входные файлы копируются в неизменяемый комплект до сборки: их редактирование
после построения плана не должно незаметно изменить запущенную операцию.

Удаление пользовательского файла из декларации удаляет его из нового корня,
если другого владельца нет. Если файл заменял пакетный конфиг, восстанавливается
конфиг из пакета нового релиза. Старое содержимое не переносится автоматически.

Сначала используем отдельные drop-in файлы. Общего механизма редактирования
произвольных INI/JSON/YAML конфигов «по ключам» в MVP нет. Типовые настройки
реализуются конкретным модулем; остальные конфиги подключаются целиком.
Произвольные `before_build`/`after_build` hooks в декларации не предлагаются.

Копирование файла не гарантирует корректность его содержимого для программы.
Известные модули запускают соответствующие валидаторы, например проверку sshd.
Для остальных конфигов нужно отдельно добавить проверку в поддерживаемый модуль
либо оценить результат пробной загрузки.

## Постоянные каталоги и совместимость

`persistent.directories` добавляет явные writable исключения внутри `/etc`.
Идентификатор `id` стабилен и выбирает каталог состояния; имя пути назначения
не является автоматически командой переноса данных. Владельцы и режим обязательны.

- Произвольные постоянные монтирования вне `/etc`, отдельные файлы и рекурсивный
  OverlayFS над `/etc` в API MVP не предлагаются.
  `/home`, `/var`, состояние looom и runtime-монтирования принадлежат системному рецепту.
- Отдельные writable файлы откладываются: программы часто сохраняют их заменой
  через rename. Позже для них понадобится ресурс с проверенным способом записи.
  Это ограничение MVP, а не изменение принятой цели поддержки явных файлов и каталогов.
- Новый локальный каталог в MVP должен перекрывать отсутствующий либо пустой
  пакетный каталог. Перенос существующего пакетного содержимого требует отдельной
  миграции; молчаливого копирования при сборке нет.
- Начальная установка или отдельная журналируемая подготовка создаёт необходимые
  каталоги до пробной загрузки. Сборка пакетов не получает общий `/home`, `/var`,
  локальные конфиги, credentials и ESP в качестве рабочих каталогов.
- Правила монтирования гарантируют доступность состояния до зависимых служб.
- Удаление объявления убирает монтирование из нового релиза, но не удаляет данные.
  Старые релизы сохраняют свои объявления и доступ к соответствующему состоянию.
- Изменение пути, ID, владельца или режима существующего локального ресурса,
  а также несовместимые требования модулей требуют явной миграции.
  Пока механизма миграций нет, такие изменения блокируются до публикации.
- Возврат удалённого объявления возможен с тем же контрактом. ID сохраняются
  в регистре состояния и не выдаются другому ресурсу автоматически.
- Никакая такая декларация сама по себе не доказывает совместимость данных служб.
  В MVP нет автоматических миграций общего состояния при активации или откате.

## Lock, воспроизведение и план

`base.lock` содержит полное замыкание пакетов: версии, архитектуру, репозитории,
источники архивов, хэши архивов и подписей, данные для проверки доверия,
состояние репозиториев и выбранных поставщиков зависимостей.
Он также идентифицирует профиль и рецепты, которые расширили запрос пакетов.

Lock связан с нормализованным пакетным запросом. Изменение hostname или содержимого
кастомного конфига само по себе не требует разрешать версии заново; изменение
профиля, источников, ядра, состава модулей или запросов пакетов требует обновить lock.
Снимок всех входов конкретного релиза фиксируется отдельно, включая конфиги,
версии рецептов, сведения о сборщике и привязку загрузочного образа к машине.
Исходные рецепты и пакеты должны быть доступны для воспроизведения; одного хэша мало.

Создание или обновление lock — явная операция. Если lock отсутствует, устарел либо
неполон, сборка останавливается. Ни сборка, ни просмотр плана не должны молча
получать свежие версии. Контрольные суммы не заменяют проверку подписей.
Недоступный архив пакета не заменяется другой версией.

План сравнивает кандидат с выбранным релизом и показывает:

- все изменения пакетов, включая транзитивные зависимости и причины включения;
- изменения файлов и их эффективных владельцев;
- состояния units, аккаунты и ссылки на credentials без значений секретов;
- локальные монтирования, конфликты и требования миграции;
- соответствующее ядро, проверки и ориентировочную потребность в диске.

Оценка свободного места не является гарантией: ENOSPC во время операции
обрабатывается как полноценный отказ с возможностью восстановления.

## Парсинг и композиция

- Одно YAML-описание со `schema: 1`. Неизвестная версия отклоняется.
- YAML 1.2 в ограниченном подмножестве: строки, числа, boolean, списки и отображения.
  Один документ; дубли ключей, custom tags, anchors, aliases и merge keys запрещены.
- Неизвестные поля, неверные типы, повторяющиеся элементы, некорректные режимы
  и конфликтующие пути — ошибки с местом в исходном документе.
- Нет автоматической подстановки переменных окружения, выполнения команд,
  удалённых include и зависимости от текущего рабочего каталога.
- В MVP один пользовательский `base.yaml`, без системы наследования и deep merge.
  Встроенные профили и модули уже обеспечивают повторное использование.
  Локальные imports и правила явного override — отдельное последующее расширение.
- Внутренняя типизированная модель независима от YAML. При необходимости другой
  входной формат или внешний генератор может формировать ту же модель.

## Исполнение и команды

Предлагается один Rust CLI без постоянно работающего daemon. Внутренние модули:
конфигурация и валидация, планирование, пакетный backend, сборщик,
управление релизами/загрузкой, журнал и восстановление.
Внешние инструменты вызываются с явными аргументами; декларация не является shell-кодом.
Перенос проверенного прототипа выполняется постепенно с сохранением VM-проверок.

Предлагаемые команды, пока не реализованный интерфейс:

```text
looom check                 проверить декларацию без применения
looom lock                  явно разрешить и зафиксировать пакетный состав
looom plan                  показать полный план при согласованном lock
looom build                 собрать и проверить отдельный корень
looom publish <release>     опубликовать подготовленный релиз
looom try <release>         назначить однократную загрузку
looom confirm               подтвердить текущий релиз после проверок
looom rollback <release>    выбрать ранее подтверждённый релиз
looom recover               восстановить незавершённые операции
```

`try` и `rollback` меняют выбор загрузки; перезагрузка — отдельное явное действие.
Автоматическое `apply`, privileged daemon, GUI и пользовательские приложения
не входят в первый интерфейс. Проверки схемы и чистого планирования не требуют VM.

Операции изменения состояния сериализуются. Их этапы журналируются с устойчивой
записью и возможностью повторного выполнения. Полностью сохранённые корень и UKI
должны существовать до включения записи в меню. Между Btrfs и ESP нет единой транзакции;
журнал фиксирует, какие шаги закончены и что требуется для восстановления.

Метаданные происхождения релиза не меняются после сборки. История подтверждений
и ссылки на текущую/постоянную/следующую загрузку хранятся отдельно: повторная
пробная загрузка старого релиза не переписывает его происхождение.

Очистка не следует автоматически за сборкой. Будущий GC защищает текущий,
постоянный, ожидающий загрузки и аварийный релизы, а также как минимум один
дополнительный подтверждённый релиз для отката. Данные пользователя, credentials
и локальные каталоги не удаляются GC релизов. Перед удалением нужен просмотр плана.

## Решения для обсуждения

1. Принять YAML как строгий формат данных и Rust как язык менеджера?
2. Достаточно ли для MVP типовых модулей плюс целых конфигурационных файлов?
3. Принять явную замену пакетных конфигов и запрет конфликтов с системными модулями?
4. Начать с постоянных каталогов, отложив writable отдельные файлы и миграции?
5. Оставить обновление lock, публикацию и перезагрузку отдельными операциями?

После согласования: машинная схема/типизированная модель, проверки конфликтов
и планы без VM; затем тестирование отказов и сквозной MVP на существующей VM.
