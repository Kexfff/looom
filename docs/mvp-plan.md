Первый рубеж: два согласованных загрузочных релиза с read-only корнем,
сохранением локальных настроек и пользовательских данных при откате.

Рабочий вариант загрузки в этом плане — GRUB + UKI, в рамках предпочтения
GRUB или Limine. Переход на Limine потребует замены интеграции меню и пробной загрузки,
а не устройства корневых релизов.

## 1. Подготовить VM и восстановление

- QEMU с UEFI/OVMF, по возможности KVM; ускорение проверяется при запуске.
- Начальные ресурсы: 4 vCPU, 8 GiB RAM, 64 GiB диска, VirtIO-диск и сеть.
- Secure Boot и шифрование отключены.
- GPT: ESP 2 GiB FAT32, остальное — один раздел Btrfs.
- Arch ISO остаётся доступным для аварийной загрузки.
- Последовательная консоль доступна с хоста; переменные UEFI сохраняются между стартами.

Для диагностики нужны две независимые линии доступа: SSH после запуска системы
и консоль для ошибок до запуска сети. Снимки виртуального диска используются для
страховки экспериментов; откат продукта проверяется через выбор корневого релиза.

**Готово:** VM загружается в UEFI, диск виден, консоль работает, ISO можно загрузить повторно.

## 2. Установить начальную систему и подключить SSH

Начальная раскладка Btrfs:

| Подтом | Назначение |
| --- | --- |
| `@bootstrap` | Начальная обычная система, временно read-write |
| `@home` | Домашние каталоги |
| `@var` | Изменяемые данные сервисов, журналы, кэш |
| `@state` | Состояние looom, локальные настройки, защищённые учётные данные |
| `@build-<id>` | Создаётся на время сборки |
| `@root-<id>` | Создаётся при публикации готового релиза |

Подтомы создаются на верхнем уровне Btrfs. ESP монтируется в `/efi`,
`@state` — в `/var/lib/looom`; `/run` и `/tmp` временные.

- Установить базовый Arch, ядро, firmware, Btrfs-инструменты, GRUB и инструменты initramfs.
- Настроить сеть, SSH по ключу, одного пользователя с фиксированным UID/GID и sudo.
- Зафиксировать начальную конфигурацию и состав пакетов; приватные данные в Git не попадают.
- Перенести базу pacman в путь внутри корневого подтома и настроить `DBPath`
  **до подключения общего `/var`**, чтобы не потерять или не смешать базу пакетов.
- Сохранить работоспособную начальную загрузочную запись на время экспериментов.

**Готово:** обычная система загружается с виртуального диска, SSH и sudo работают;
база pacman относится к установленному корню. Проверить доступность общей `/var`
и отсутствие скрытых нужных данных под точками монтирования.

## 3. Проверить изменяемое состояние при read-only /etc

- В начальной системе проверить read-only представление `/etc` и локальные
  исключения, сохраняя возможность вернуться к обычной загрузке `@bootstrap`.
  Полностью read-only корень проверяется на этапе 4.
- Выбрать и проверить способ предоставления данных пользователей через NSS/PAM.
  Имя и UID/GID личного пользователя заданы конфигурацией; password hash хранится
  вне релизов и предоставляется системе при запуске.
- Проверить вход по ключу, вход с паролем в консоль и смену пароля.
- Подключить постоянный тестовый каталог `/etc/looom-local` из `@state`.
- Подготовить монтирования и зависимости сервисов так, чтобы локальные данные
  были доступны до использования; отсутствие обязательного хранилища обнаруживается.
- Проверить постоянный machine-id и необходимые изменяемые данные сервисов.

**Готово:** read-only `/etc` работает с явно выбранными исключениями;
пароль не находится в публикуемом корне, Git, lock или UKI;
локальный каталог изменяется и сохраняется после перезагрузки.

Этот этап — технический эксперимент. Нельзя считать простой bind mount
отдельного файла готовой поддержкой программ, заменяющих его через rename.
При выборе нестандартного средства смены пароля оно должно быть явно описано.

## 4. Создать и загрузить первый релиз v1

- Собрать новый корень в `@build-<id>` из пакетов и конфигурации.
- Сборка использует собственное рабочее состояние `/var`; постоянные `@home`,
  `@var`, `@state` и рабочая ESP не предоставляются пакетным скриптам для записи.
- Внутри сборки доступны её база pacman, необходимые виртуальные файловые системы
  и отдельно разрешённый кэш пакетов.
- Сгенерировать initramfs и UKI с выбранным ядром и явными параметрами нужного
  корневого подтома. Не наследовать параметры загрузки работающего `@bootstrap`.
- Проверить согласованность ядра, модулей, базы пакетов и конфигурации.
- Финализировать сборку в read-only `@root-v1`; опубликовать UKI и запись GRUB
  только после сохранения всех данных.
- Загрузить v1, проверить состояние монтирований, вход и SSH.

**Готово:** v1 загружается; `/` read-only, `/home` и выбранное состояние read-write;
запись в системные файлы отклоняется; запрос списка пакетов работает.

## 5. Создать v2 и доказать ручной откат

- Изменить декларативную настройку и набор тестовых пакетов, собрать v2.
- Для начального опыта можно использовать тот же согласованный пакетный архив:
  изменение конфигурации и состава пакетов уже отличает корни.
- Загрузить v2 и проверить изменения.
- Изменить локальный тестовый каталог, пароль и создать файл в `/home`.
- Выбрать v1 в GRUB и перезагрузиться.
- Проверить: декларативная настройка и пакеты вернулись к v1; локальная настройка,
  новый пароль, пользовательский файл и правильные владельцы сохранились.
- Отдельным опытом обновить весь согласованный пакетный набор, включая ядро,
  и проверить правильность пары «UKI + модули + корень» и возврат к старому ядру.

**Готово:** возврат к прежнему релизу не требует ремонта пакетов или файлов;
смена версии ядра также откатывается согласованно.

## 6. Добавить пробную загрузку и проверить прерывания

- Подтверждённый релиз — постоянный выбор GRUB; кандидат назначается однократно.
- Проверить, что GRUB действительно очищает `next_entry` до запуска ядра.
- Первоначально подтверждать релиз вручную после проверки; затем добавить
  автоматические проверки обязательных монтирований и сервисов.
- Проверить намеренно неисправный кандидат: после перезапуска выбирается
  последний подтверждённый релиз. Зависшую VM перезапускаем с хоста.
- Прервать сборку, публикацию и запись загрузочного состояния; проверить восстановление.
- Проверить недостаток места и повторный запуск после незавершённой операции.
- Выбрать и проверить аварийный путь при повреждении меню или состояния GRUB.
- Очистка сохраняет работающий, ожидающий проверки и последний подтверждённый релиз.

**Готово:** проверенные сбои не делают единственный рабочий релиз недоступным;
незавершённые операции обнаруживаются. Тесты VM не заменяют последующую проверку
устойчивости записи на реальном накопителе.

## 7. Автоматизировать проверенную механику

- Ввести схему `base.yaml` и пакетный `base.lock`.
- Добавить операции: сборка, список релизов, публикация, выбор следующей загрузки,
  подтверждение, откат, очистка.
- Сохранять журнал операций и метаданные релизов.
- Проверять конфликт локальных и декларативных путей, несовпадение UID/GID,
  отсутствие пакетов и загрузочных артефактов.
- Сборка соответствует декларации: удалённые пакеты и настройки не наследуются.
- Повторное применение YAML не создаёт неописанных изменений в общем состоянии.

**Готово:** цикл v1 -> v2 -> v1 выполняется инструментом, с понятным результатом
и теми же гарантиями, которые проверены вручную.

## 8. Подключить рабочий стол и приложения

- Добавить KDE Plasma, SDDM, графику VM, звук, сеть и требуемые desktop portals в базу.
- Проверить графический вход, сохранение настроек и смену пароля выбранным способом.
- Добавить пользовательский Flatpak и rootless Podman/Distrobox, затем `apps.yaml`.
- Собрать два desktop-релиза; установить приложение и проверить его данные
  после отката между этими релизами.
- Проверить успешную загрузку на уровне графической сессии.

**Готово:** рабочий стол и пользовательские приложения переживают проверенный
цикл обновления и отката; затем выбираем реальное оборудование и профиль CachyOS.

и GC с защитой выбранных/смонтированных корней; см. [журнал](runs/2026-10-09-generations-gc/README.md).

Разработку и разрушительные испытания продолжаем только на VM.
Затем пользовательские Flatpak/rootless контейнеры и проверка их данных при откате.
