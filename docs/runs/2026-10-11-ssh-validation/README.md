# Проверка SSH при сборке релиза

Дата: 2026-10-11. Пользователь сообщил о двух строках `Unable to load host key`
после генерации UKI на системе, установленной из первого looom ISO.

Это серверные host keys, автоматически создаваемые установщиком и импортируемые
в `/var/lib/looom/ssh`. Они удостоверяют компьютер; пользовательский
`authorized_keys` определяет разрешение входа. Пустое поле SSH public key в
мастере не отменяет создание серверной идентичности.

Причина предупреждения: `sshd -t -o HostKey=/etc/ssh/looom-validation.key`
добавляет временный ключ, но сохраняет два HostKey из управляемого drop-in.
Постоянный State с настоящими закрытыми ключами не подключается к build root.
OpenSSH успешно проверяет временный ключ, одновременно предупреждая о двух
недоступных постоянных ключах. Эти строки сами по себе не означают отказ сборки.

В Rust выделена проверка `validate_sshd`: в приватном build root временно
заменяются только два управляемых HostKey на одноразовый Ed25519-ключ.
Проверяется весь SSH-конфиг вместе с Includes. Оригинальный drop-in
восстанавливается, временный каталог ключей удаляется до продолжения сборки.
Восстановление и уборка выполняются также при отказе `sshd`; их собственные
ошибки останавливают сборку. Настоящие ключи компьютера в build root не копируются.

## Воспроизведение и проверки

Всё выполнялось только в development VM `Cachyos`, MAC `52:54:00:7b:23:63`,
UEFI/KVM. Рабочий read-only релиз `rust-gc-ready` не менялся. Сохранённый
`@toolchain-20261006` смонтирован в `/var/lib/looom/dev/root`, исходники
`/var/lib/looom/dev/src` подключены внутрь как `/workspace`.

```sh
arch-chroot /var/lib/looom/dev/root bash -c '
  cd /workspace &&
  cargo fmt &&
  cargo clippy --locked --all-targets -- -D warnings &&
  LOOOM_TEST_VM=1 cargo test --locked -- --nocapture --test-threads=1 &&
  cargo build --locked --release --bin looom
'
```

Новый тест использует отдельный writable Btrfs snapshot toolchain и настоящий
OpenSSH `10.5p1`, без постоянных host keys. Старая команда возвращает success,
а захваченный stderr содержит обе показанные пользователем строки. Исправленная
проверка принимает валидный конфиг, но отклоняет неизвестную директиву в отдельном
включаемом файле. В обоих случаях проверены точное восстановление drop-in,
отсутствие временных ключей и отсутствие постоянных ключей в тестовом root.
Snapshot размонтируется и удаляется; при ошибке уборки сохраняется для проверки.
В финальном журнале нет `Unable to load host key` от новой проверки; сообщения
`LooomInvalidDirective` ожидаемы и относятся к отрицательному тесту.

Результат: новый тест и все прежние 11 интеграционных тестов прошли; Clippy
без предупреждений, release-бинарник собран. [Финальный журнал](rust-final.log).
Публичный журнал проверен на исходной VM до экспорта на отсутствие её credentials.
[Результат аудита](public-audit.log), [SHA исходника](source.sha256),
[SHA бинарника](binary.sha256).
Бинарник сохранён локально как `.local/artifacts/looom-0.2.0-ssh-validation-20261011-x86_64`;
он не заменяет бинарник в опубликованном ISO.

Локально выполнялись только чтение, редактирование, передача файлов и сравнение
SHA. Пользовательская новая VM, Intel N100 и опубликованный ISO
`v0.2.0-alpha.1` не изменялись. Исправление доступно в исходниках; старый ISO
продолжает содержать прежний бинарник.
