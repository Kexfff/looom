# Выбор диска и VM без serial — 2026-10-10

Исправление пользовательского отказа: обычный virtio-диск 64 GiB в Arch ISO
имеет пустые SERIAL/WWN. Раньше мастер принимал только путь `/dev/vda`, показывал
также loop/CD-ROM и требовал настроить serial после остальных вопросов.
Теперь реальные диски пронумерованы; `Disk number to erase` принимает номер.
Занятые, read-only и неподдерживаемые диски показываются с причиной отказа.
Некорректный номер предлагает повторить выбор; `0`/Enter отменяет установку.
Подходящий диск проверяется до вопросов о пользователе и ещё раз после них.

В распознанной VM разрешён диск без serial/WWN. Строгий план дополнен
`disk.session_identity`: kernel boot UUID, canonical sysfs path и `diskseq`.
Для дисков с serial/WWN поле отсутствует. Повторная запись сверяет идентичность
перед каждым этапом, включая разметку после длительного получения пакетов.
Замена диска по тому же пути и новая live-загрузка не разрешают старый план.
Мастер явно показывает ограничение одной live-сессии и фразу
`ERASE /dev/vdb NO-ID 68719476736`. Полный путь остаётся в плане и подтверждении;
номер — только способ интерактивного выбора. Физический диск по-прежнему требует
serial/WWN. При недоступном `diskseq` необходим настроенный serial VM.

## Воспроизведение и проверки

Сборка, fmt, Clippy и **все тесты только в VM**. Рабочий компьютер используется
для редактирования, Git, SSH и управления гипервизором. Основная разрешённая VM
`Cachyos`: 6 vCPU/8 GiB, UEFI, рабочий диск 60 GiB, подтверждённый rust-gc-ready.
Для проверки добавлен отдельный пустой virtio-диск 64 GiB **без serial и WWN**.
Образ хранится на постоянном диске, не в host `/tmp`.

[VM-only контроллер](../../../scripts/test-installer-selection.py) требует root,
MAC основной VM, QEMU/KVM и явно выделенный `/dev/vdb` размером 64 GiB без ID.
Пароли берутся из закрытого старого тестового fixture только внутри VM, в
аргументы и публичный вывод не передаются. Действующий диск не форматируется.

В отдельном toolchain chroot `/workspace`:

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked --bin looom
LOOOM_TEST_VM=1 cargo test --release --locked -- --test-threads=1
```

Проверенный бинарник скопирован в закрытый
`/var/lib/looom/dev/installer-selection-20261010/looom`.
Контроллер внутри development VM:

```sh
python /var/lib/looom/dev/installer-selection-20261010/test-installer-selection.py negatives
# На гипервизоре: detach/attach того же собственного пустого vdb без serial.
python /var/lib/looom/dev/installer-selection-20261010/test-installer-selection.py replugged
python /var/lib/looom/dev/installer-selection-20261010/test-installer-selection.py install
```

Подтверждено:

- В меню только два целых диска с номерами: занятый `/dev/vda` и доступный `/dev/vdb`.
  CD-ROM и loop отсутствуют; неправильные номера и занятый диск не проходят.
- Ранняя отмена и отмена перед стиранием сохраняют начало/конец пустого диска.
- Настоящие TTY-пароли скрыты; несовпадающие root/user пароли отвергаются до записи.
- Создание и чтение плана VM без ID успешны. Подмена boot UUID или diskseq
  отвергается; новое реальное подключение того же образа делает прежний план
  недействительным. Проверено до форматирования.
- Полный интерактивный мастер с выбором по номеру, hostname `looom3`, user `kexfff`,
  публичным SSH-ключом и точным подтверждением устанавливает Arch/Plasma.

Первый запуск PTY-контроллера обнаружил гонку самого теста: rpassword печатает
приглашение перед переключением режима TTY, и контроллер успевал проверить echo
слишком рано. Он исправлен: ждёт отключения echo **перед отправкой пароля**, затем
проверяет отсутствие plaintext в выводе. Исправленные проверки прошли для обоих
паролей; ошибочная предварительная попытка не считается результатом.

## Самостоятельная загрузка

Установленный диск отключён от development VM и подключён как единственный
`/dev/vda` отдельной UEFI VM: 4 vCPU, 4 GiB, Secure Boot выключен. Диск остаётся
без serial/WWN. Проверяются read-only `@root-initial`, точный пакетный состав,
исправные аккаунты, hostname `looom3`, UID 1000 пользователя `kexfff`, работающие
NetworkManager/sshd/SDDM и отсутствие failed units. `verify`/`confirm` закрепляют
релиз. [Фактическая загрузка](evidence/first-boot.log).

Development VM сохранила прежний профиль, credential-хэши, recovery UKI,
текущий релиз и saved/next; тестовая UEFI-запись удалена, исходный BootOrder
восстановлен. [Проверка](evidence/primary-preserved.log).

Первый XML новой acceptance VM унаследовал serial из старого шаблона. Он удалён
и загрузка повторена с пустыми SERIAL/WWN; первоначальный прогон не считается
доказательством загрузки без ID.

## Граница

Это дополнение к [предыдущей приёмке](../2026-10-09-installer/README.md),
не самостоятельная повторная проверка всех failpoints менеджера. Планы без ID
не переносятся между live-загрузками или переподключениями. Для восстановления
после перезагрузки live-среды нужно заранее настроить serial/WWN и сохранить
workspace на другом постоянном диске. Шифрование, dual boot и Calamares не добавлены.
