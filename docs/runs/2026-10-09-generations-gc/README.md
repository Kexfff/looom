# История bootstrap и сборка мусора на VM

Дата: 2026-10-09. Продолжение [bootstrap recovery](../2026-10-09-bootstrap-recovery/README.md).
Все сборки, форматирование, проверки и разрушительные опыты выполняются только
на разрешённой VM Cachyos (`192.168.122.91`, MAC `52:54:00:7b:23:63`).
Локальный компьютер служит редактором и SSH/libvirt-клиентом; N100 не изменяется.

## Контракт

`looom bootstrap-update <confirmed-running-release> [generation-id]` позволяет
создать несколько аварийных поколений из одного подтверждённого релиза.
Без второго аргумента имя поколения совпадает с именем исходного релиза.
Для повторного обновления выбирается новое уникальное имя. Повтор незавершённой
операции требует прежние источник, имя и SHA-256 менеджера.

Каждое поколение получает `@bootstrap-<generation-id>` и закрытый каталог
`State/bootstrap-history/<generation-id>` с журналом и Btrfs-копиями EFI.
`State/bootstrap-current.json` — атомарно записываемый указатель активной операции.
Сначала сохраняются журнал и копия старого стабильного EFI; затем переключается
указатель, и только потом создаётся кандидат. Одновременные операции сериализует
общий `release-control.lock`. Пробная загрузка/проверка/commit прежние:
`bootstrap-try`, reboot, `bootstrap-confirm`. Постоянный рабочий релиз не меняется.

Существующий schema-1 singleton импортируется в историю при следующем обновлении;
его исходный каталог сохраняется как закрытая совместимая резервная копия.
`bootstrap-list` показывает поколения и активную операцию. Рабочее меню содержит
стабильную и предыдущую аварийные системы; старые поколения не публикуются все
сразу на ESP. Встроенная emergency-запись GRUB по-прежнему использует фиксированное
имя стабильного UKI. Schema-2 журнал связывает поколение, подтом и источник строго;
неизвестные поля, ссылки и несовпадение machine identity отклоняются.

При откате на релиз с прежним singleton-менеджером загрузка, `verify` и выбор
обычных релизов остаются доступными. Он не понимает новую историю bootstrap:
для её обслуживания используется новый менеджер из актуального аварийного
поколения (либо сохранённый новый бинарник). Старый `recover` не следует применять
к новой истории; он отказывает при неизвестном bootstrap digest. Обратная
совместимость будущих миграций State остаётся отдельным требованием к версиям.

`looom gc [--keep N]` — предварительный просмотр. `--apply` разрешает удаление.
`N >= 2`: сохраняются последние N подтверждённых обычных релизов по времени
создания и имени при равенстве. Независимо от N сохраняются работающий релиз,
все выбранные GRUB targets, все смонтированные корни и вложенные каталоги
(включая bind из другого подтома и tmpfs),
источники незавершённых bootstrap-поколений и configured-сборок.
Опубликованные неподтверждённые релизы сохраняются до явного `reject`.

Для bootstrap сохраняются активная операция, стабильный/предыдущий EFI-корень
и все смонтированные поколения. Удаляются лишь завершённые, более не используемые
поколения из проверенной истории. Завершённый фиксированный candidate EFI тоже
удаляется после проверки SHA и отсутствия выбора в GRUB.

Обычный релиз проходит `removing` → durable menu → Btrfs delete с commit →
EFI unlink + syncfs → `removed` в журнале операций → удаление release metadata.
Аварийное поколение проходит `removing` → Btrfs delete → удаление закрытых EFI
checkpoints → `removed`; его журнал остаётся. `recover` продолжает уже начатое
удаление, проверяя защиту заново. Он не начинает новый GC по собственной инициативе.
Ссылки, чужие файловые системы и неподходящие владельцы/права останавливают удаление.

GC сохраняет `/home`, `/var`, State credentials, локальные настройки, frozen inputs,
evidence, журнал операций и неучтённые подтомы. Кэш пакетов и private build roots
пока имеют отдельный жизненный цикл. Удаление устаревших входов сборки — отдельная
будущая политика; текущий GC освобождает корни и EFI.

## Воспроизведение

Компилятор находится в отдельном writable `@toolchain-20261006`. Рабочий read-only
корень не заменяется вручную. В chroot с исходниками `/workspace`:

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
LOOOM_TEST_VM=1 cargo test --release --locked -- --test-threads=1
cargo build --release --locked
```

Приёмочные `looom-vm-gc` и `looom-vm-test` не устанавливаются в релизы.
`looom-vm-gc prepare` сохраняет исходные credential-хэши в закрытом VM-only
каталоге; `negatives` изменяет и восстанавливает только ready-журнал,
`report` сравнивает пароли/runtime, пакетный состав, frozen source и профиль,
`audit` проверяет публичные артефакты перед экспортом. Приватный baseline не экспортируется.

Runtime fixture использует любой сохранившийся подтверждённый корень, а не
исторический `mvp-b`, и отдельный FAT-образ 512 MiB. Он проверяет preview,
защиту saved/next, смонтированных корней, вложенных bind/tmpfs и configured-сборок;
отказ удаления ссылки, допустимое имя релиза из 64 символов и прерывания `gc-journal`, `gc-menu`,
`gc-root`, `gc-uki`. После удаления старых настоящих поколений тест запускается снова.

## Результаты

Проверки Rust прошли до и после удаления старых релизов: Clippy без warnings,
5 config tests + isolated bootstrap + runtime suite. Форматирование/сборка только
на VM. Сначала обновлённый runtime fixture выявил свои старые допущения:
FAT 128 MiB не вмещал новый UKI и одна строка ещё использовала старое имя.
Исправлены размер fixture и динамическое имя; это не ошибки рабочего диска.

Реальный GC удалил 14 старых обычных релизов, сохранив `rust-bootstrap-recovery`
и `rust-upgrade-1007`. Доступное место: Btrfs 23 → 42 GiB, ESP 178 MiB → 1.4 GiB.
Frozen inputs/operations и пользовательские данные сохранились.

Первый hard stop после удаления `@root-broken` выявил пустой FAT `grub.cfg`.
VM загрузилась в прежний read-only `rust-bootstrap-recovery`; SSH был доступен,
но `verify` правильно отказал из-за отсутствующей записи меню. `recover`
восстановил меню и завершил удаление, после чего `verify` прошёл. В GC добавлен
`sync -f <ESP>` **между записью меню и удалением корня**. Повторный hard stop
на отдельном непубликуемом `gc-powercut-sync` fixture сохранил меню (1107 bytes),
и `verify` прошёл до вызова `recover`; тот завершил оставшиеся EFI/metadata шаги.
Это два конкретных опыта QEMU/KVM, а не гарантия FAT при любом обесточивании.

Миграция старого schema-1 singleton проверена с прерываниями
`bootstrap-generation-prepared` (указатель ещё отсутствует) и
`bootstrap-generation-selected` (активная операция staging). Повтор команды
и `bootstrap-recover` сохраняют рабочий saved target и возобновляют кандидата.

`gc-recovery-a` и `gc-recovery-b` последовательно собраны из одного подтверждённого
`rust-bootstrap-recovery`, загружены writable с Linux 7.2.9 и подтверждены native
health checks. После первого подтверждения reboot вернул прежний saved read-only
релиз. Повтор завершённой команды оказался идемпотентным.

Ready-кандидат отклонил восемь неправильных журналов (generation/source/root
traversal, schema, phase, manager SHA, machine identity, unknown field), два
некорректных указателя (traversal, отсутствующий журнал) и попытку подтверждения
из работающего read-only релиза. Профиль, стабильный UKI и saved/next не изменились.

После подтверждения B исходное аварийное `@bootstrap-rust-upgrade-1007` стало
устаревшим. GC отдельно прерван после journal и root delete; `recover` завершил
удаление checkpoints и сохранил запись `removed`. Текущий B и предыдущий A
сохранены. Исходный singleton остаётся закрытой копией для диагностики;
неучтённый первоначальный `@bootstrap` не удаляется.

Следующее `gc-recovery-final` проверило финальную на тот момент сборку; GC
сохранил смонтированное A, после unmount прерванное удаление A завершил `recover`.
Предыдущее B затем действительно загружено отдельной one-shot записью GRUB:
Linux 7.2.9, rw корень, sshd/NetworkManager/accounts/guest agent active, failed units
отсутствуют. Saved read-only выбор сохранён.

`rust-gc-generations` собран/опубликован/загружен/подтверждён с 651 пакетами.
Перед выпуском добавлена отдельная защита mount targets: проверка одного FSROOT
не учитывала бы bind из State либо tmpfs внутри удаляемого корня. Runtime suite
успешно проверил оба случая, вложенный bind, configured journal, symlink refusal,
64-символьный release ID и четыре прерывания удаления. Дополнительные сборки
`gc-recovery-checked` и `rust-gc-ready` содержат это окончательное исправление.

`gc-recovery-checked` загружен и подтверждён, старое B очищено; сохранились
checked и previous final. Окончательный read-only `rust-gc-ready` загружен,
`verify` и `confirm` прошли. Установленный native `looom-password --stdin`
сменил временный тестовый пароль. PAM login/SDDM/sudo принимает его и отклоняет
неправильный; фактически запущены Plasma/KWin Wayland и PipeWire/Pulse/WirePlumber.

Откат в `rust-gc-generations` проверен собственным установленным менеджером
того релиза: `verify`, PAM login/sudo, новый пароль, файлы в `/etc/looom-local`
и `/home/codex`, UID/GID владельца сохранились. Через его native CLI назначен
возврат в `rust-gc-ready`. Публичные артефакты проверяются до восстановления
временного пароля и после него; исходные root/user хэши сравниваются только
в закрытом VM baseline. Финальный отчёт фиксирует восстановление исходного пароля.

Логи, итоговые метаданные и SHA-256 manifest находятся в `evidence`.


## Итоговое состояние

VM оставлена в подтверждённом `rust-gc-ready`: `/` read-only, Linux
7.2.9-arch1-1, 651 подписанный пакет из Arch Archive 2026-10-07. Saved GRUB
`looom-rust-gc-ready`, next пуст. Предыдущий рабочий `rust-gc-generations`
сохранён. Аварийные поколения: `gc-recovery-checked` и previous
`gc-recovery-final`; три устаревших поколения имеют журнал `removed`.
Исходные root/user credential-хэши и runtime восстановлены/сверены; временного
password-test каталога нет. Plasma Wayland и audio services активны;
failed units отсутствуют; compiler root unmounted.

Native manager SHA-256: `a8481da9c1bc559fdbf4dac7a9f134dcedddfa4f018481bb30807daa581abbbf`. Его frozen lock находится в
[`configs/native/gc/base.lock`](../../../configs/native/gc/base.lock), YAML —
[`base.yaml`](../../../configs/native/gc/base.yaml). Исходники bootstrap
совпали с 14 файлами проверенной VM-сборки; отдельно сверён `bootstrap_update.rs`
в установленном рабочем релизе. Итоговое доступное место: Btrfs **39 GiB**, ESP
**1.2 GiB** (перед началом: 23 GiB / 178 MiB). Дополнительный диск не понадобился.

Экспортированы только **98** проверенных публичных файлов, включая
[`SHA256SUMS`](evidence/SHA256SUMS). Аудит выполнен с временным паролем до его
удаления и после восстановления исходных значений. Whole State, хэши паролей,
SSH private keys, private baseline и корни систем не экспортировались.

Границы: исходный singleton backup, frozen inputs, package cache и неизвестные
подтомы сохраняются. GC здесь не является автоматическим daemon/таймером.
Испытаны конкретные journal checkpoints и два hard stop VM; физическое
обесточивание накопителя не моделировалось. Ранее наблюдавшийся редкий сетевой
сбой не воспроизвёлся, его причина остаётся не установленной.
